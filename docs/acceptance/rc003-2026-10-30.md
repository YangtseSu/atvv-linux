`VOICECOMMAND` and then `ASSISTANT` during the 2026-10-30 consumer-key

journal records the ATVV source at 16 kHz during that period.

Step 11 update (after this acceptance run): the code default trigger is now
`DICTATE` (`KEY_DICTATE`); vinput keeps the user's entries and adds `Dictate`
at the next free index (the live config's index was `2=`); `F24` remains a raw
configurable key, not a fallback. A workspace build of the step-11
daemon ran against the same RC003: it emitted `KEY_DICTATE`, streamed
104 frames / 24,960 samples on a physical press, and fcitx5-vinput recorded
from `atvv-miremote-rc003` at 16 kHz. The installed `0.1.0-3` package
described above still ships the `F24` default; this record is unchanged for
that package.

Index note: the `2=` above is that live configuration's next free index,
because it already had entries `0` and `1`. A default vinput install has only
`[TriggerKey] 0=Alt_R`, so the next free index is `1=Dictate`. Current docs
use the default-install form; never hard-code `2=` from this record.

Fallback note: `F24` was a temporary experiment, not a fallback.
`VOICECOMMAND` and `ASSISTANT` are the supported fallbacks; the declared set
is `DICTATE`, `VOICECOMMAND`, `ASSISTANT`.

## Post-reboot connect fix (2026-10-30)

After installing `0.1.0-1` and rebooting, `atvvctl doctor` reported:

```text
daemon     fail GetStatus failed: org.freedesktop.DBus.Error.ServiceUnknown:
           The name is not activatable
```

`atvvd.service` was in a restart loop. `BluezLink::connect` propagated
`org.bluez.Error.InProgress` from a pending BlueZ connect, `atvvd` exited, and
systemd restarted it every 2 s. The remote was asleep, so the loop repeated and
the D-Bus name never stayed owned.

Fix in `0.1.0-2`:

- `BluezTransport` is lazy: `atvvd` starts without a link, owns
  `org.atvv.Daemon`, and reports `disconnected` immediately.
- `Daemon` schedules the initial reconnect; `wait_connected` treats
  `InProgress` and `AlreadyConnected` as a pending/successful connection, and
  the whole connect operation is bounded.
- The input runtime is attached when the HID-over-GATT node appears and
  retried every 2 s if discovery is too early; a dropped runtime releases the
  synthetic trigger so a held modifier cannot stick.
- Verified with the release binary while the remote was disconnected:
  `atvvctl doctor` shows `daemon`, `source`, and `pipewire` as `ok`; the
  daemon stays active and logs `reconnect failed: connect timed out after
  10s` on each retry instead of exiting.
- The physical link still requires waking the remote (press a key). BlueZ
  retained a stale `InProgress` after the reboot; `bluetoothctl connect`
  timed out until the remote woke.
